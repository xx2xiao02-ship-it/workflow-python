零、服务调用互斥与等待机制（强制）

1. 修改任何生产代码前，先检查：

- 当前视频制作控制台进程；
- tools\local_service_governance.py 的服务状态；
- 当前任务状态文件；
- 是否存在正在提交、轮询、生成、写入草稿或保存草稿的业务任务；
- 是否已有其他维护锁。

不能仅根据 Python 进程存在就判断业务任务正在运行，必须检查实际任务状态。

2. 如果发现任务处于以下状态，禁止修改代码：

queued
running
submitting
polling
creating
writing
saving
retrying

必须等待任务进入以下终态：

succeeded
failed
blocked
cancelled

等待期间：

- 每 5–10 秒检查一次；
- 不得强制结束进程；
- 不得取消任务；
- 不得修改正在使用的服务代码；
- 不得重新提交业务任务；
- 必须记录任务 ID、当前阶段和状态。

3. 进入等待前，先建立维护请求标记，阻止新的业务任务进入：

maintenance_requested = true
reason = "v3.2 编导包与音效模块升级"

新请求不得静默执行，必须返回：

MAINTENANCE_WAITING
服务正在等待当前任务完成，暂不接受新的生产任务。

如果现有系统没有维护门禁，只在当前生产任务入口增加最小门禁，不得大范围重构。

4. 所有旧任务进入终态后，再进行二次确认：

- 没有 running、queued、submitting、polling、writing 任务；
- 没有未完成的外部 API 请求；
- 没有草稿写入操作；
- 没有其他 Codex 或维护进程持有升级锁；
- 没有正在执行的业务回调。

确认通过后，使用原子方式创建维护锁：

.codex\locks\v32-upgrade.lock

锁文件至少记录：

{
  "owner": "codex-v32-upgrade",
  "pid": 0,
  "purpose": "v3.2 编导包与音效模块升级",
  "created_at": "",
  "source_revision": ""
}

5. 如果发现已有维护锁：

- 先检查锁对应的 PID 和任务状态；
- PID 仍存活时继续等待，不得覆盖锁；
- PID 已退出但任务状态不明确时，停止并报告；
- 不得直接删除或覆盖未知来源的锁文件。

6. 获得锁后，才允许执行：

读取源码快照
→ 记录文件哈希
→ 修改代码
→ 执行测试
→ 控制重启服务
→ 执行健康检查

7. 修改期间禁止启动新的外部业务任务，禁止调用真实付费 API。

8. 修改完成后：

- 先运行测试；
- 再控制重启本地服务；
- 检查服务端口和健康状态；
- 检查 v3.2 是否可加载；
- 检查 v3.1 是否仍可加载；
- 确认没有遗留任务锁；
- 最后清除 maintenance_requested；
- 最后释放 v32-upgrade.lock。

服务重启只用于加载新代码，不得自动重新执行旧业务任务。

9. 等待上限：

- 普通节点任务最长等待 30 分钟；
- 视频生成、数字人和草稿写入任务最长等待 60 分钟；
- 超时不得强杀进程，不得直接修改；
- 必须报告任务 ID、状态、阶段和阻断原因，并将升级标记为 BLOCKED。
